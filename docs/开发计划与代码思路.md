## 2. 开发策略

### 2.1 按业务闭环竖切，不按层横切

虽然代码按 `controller / service / mapper` 分层，但开发不要“先写完所有 Controller，再写所有 Service”。每个阶段应完成一条可演示的业务链路：

```text
HTTP 请求 → Controller → Service → Mapper → MySQL/Redis/Chroma → VO 返回
```

### 2.2 先打通数据，再接 AI

推荐顺序：

```text
分类 → 知识 CRUD/公共查询 → 上传/批次 → 异步向量化 → 问答 → 贡献 → 反馈 → 管理端 → 统计/收尾
```

AI 是风险最高的部分，但必须先有分类、知识、上传和向量化，RAG 才有数据可检索。

### 2.3 先用 Mock，再接真实模型

在实现向量化和 SSE 时，先定义接口：

```text
EmbeddingService   // 文本 → 向量
VectorStoreService // 向量 upsert/delete/search
LlmService         // Prompt → token 流
```

开发期可以使用 Mock 实现：

- Mock Embedding 返回固定维度向量；
- Mock LLM 按固定节奏输出 token；
- 这样能先验证任务状态机、SSE 事件顺序、前端断流，不被模型环境阻塞。

真实实现放在 `com.campusnexus.ai`，通过配置切换。

**公共查询**

```java
LambdaQueryWrapper<Knowledge> wrapper = Wrappers.<Knowledge>lambdaQuery()
        .eq(Knowledge::getStatus, 1)
        .eq(Knowledge::getDeleted, 0)
        .eq(categoryId != null, Knowledge::getCategoryId, categoryId)
        .and(StringUtils.hasText(keyword), w -> w
                .like(Knowledge::getTitle, keyword)
                .or().like(Knowledge::getQuestion, keyword)
                .or().like(Knowledge::getAnswer, keyword)
                .or().like(Knowledge::getKeywords, keyword))
        .orderByDesc(Knowledge::getCreateTime);
```

- 公共端只返回正常知识；下架/删除不可见。
- 详情方法先更新 `view_count = view_count + 1`，再查询返回；使用 `setSql` 避免读改写丢失更新。

**新增/修改规则**

- `categoryId` 必须存在且启用。
- `title/question/answer` 至少一项；填写 `question` 时 `answer` 必填。
- 新增/修改后 `vectorStatus=0`。
- 修改后清理旧向量，避免旧内容继续被检索；清理失败进入补偿任务。
- 删除采用 `@TableLogic`，检索层过滤 `status=1`；Chroma 清理异步执行并可重试。

### P3 上传 + 批次

**新增类**

```text

com.campusnexus.controller.AdminKnowledgeController # 7.4
com.campusnexus.controller.AdminImportBatchController
```

**上传流程（异步）**

```text
1. 校验文件大小/扩展名/MIME
2. FileStorageService.store(file, objectKey)
3. 生成 batchId，写 import_batch(status=PROCESSING)
4. 提交 importTaskExecutor，立即返回 HTTP 202 + batchId
5. Worker：读取文件 → Tika 解析
6. Worker：结构预切（3000-5000 字）→ LLM 生成 Q&A
7. Worker：短事务写 import_batch(status=SUCCESS) + knowledge + knowledge_chunk
8. 失败：import_batch(status=FAILED, error_message=...)
```

前端拿到 `batchId` 后轮询 7.15 批次详情，直到状态为 `SUCCESS` / `FAILED`。

**注意事项**

- 上传 HTTP 请求只负责存储文件和创建批次，LLM/解析不在请求线程里执行。
- 文件上传和解析不要放在数据库长事务里；先完成外部操作，再开短事务写库。
- 解析/生成失败时仍写一条 `import_batch(status=FAILED, error_message=...)`，方便追溯。
- `knowledge.vector_status=0`，不等待向量化。
- 批次列表/详情从 `import_batch` + `knowledge` 聚合；详情可按 `importBatchId` 复用 7.2 的知识列表。
- 导入线程池与 P4 向量化线程池分开，避免互相阻塞。
- 应用启动时把遗留的 `PROCESSING` 批次标记为 `FAILED`，避免重启后永久卡住。
- 存储先做本地实现，接口保持不变，生产替换 OSS；两个实现用 `@ConditionalOnProperty` 或 `@Profile` 切换，避免同时注册两个 `FileStorageService` Bean。
- LLM 未配置时使用 `MockKnowledgeQaGenerator` 跑通链路；生产设置 `AI_ENABLED=true` + `AI_API_KEY`。

**任务创建**

```java
String taskId = UUID.randomUUID().toString();
AsyncTask task = new AsyncTask();
task.setTaskId(taskId);
task.setTaskType(TaskType.VECTORIZE.name());
task.setStatus(TaskStatus.PENDING.name());
task.setTotal(pendingCount);
task.setCreatedBy(SecurityUtils.userId());
asyncTaskMapper.insert(task);
vectorTaskExecutor.execute(() -> handler.execute(task, sink));
return taskId;
```

**任务状态机**

```text
PENDING → RUNNING → SUCCESS
                  → PARTIAL
                  → FAILED
```

**向量化 Worker**

```text
加 Redis 锁 lock:vector
标记 RUNNING / startedAt
每批 20 条查询 status=1 AND vector_status IN (0,2) AND deleted=0
对每条：
  1. 删除旧 knowledge_chunk / Chroma 向量
  2. 重新切分/embedding
  3. Chroma upsert（id = knowledgeId:chunkIndex）
  4. 更新 knowledge_chunk、vector_status=1、vector_synced_time
  失败：vector_status=2、vector_error=...
  更新 task processed/success/failed/progress
结束：PARTIAL 或 SUCCESS，记录 finishedAt，释放锁
```

**边界**

- 任务创建时检查同类任务是否运行：Redis 锁或 `async_task` 中 RUNNING，返回 `20013`。
- 应用启动时把遗留 `RUNNING` 任务改为 `FAILED`，对应知识重置为待同步。
- 单条失败重试 2 次，继续处理后续条目。
- 7.11 任务查询同时服务向量化和批次回滚。
- 检索层只使用 `vectorStatus=1` 的知识，避免旧向量污染。


**会话**

- 3.2 创建会话：`sessionKey = UUID`，登录用户写 `user_id`，匿名写 null。
- 3.3 会话列表：仅当前登录用户，分页，按 startTime desc。
- 3.4 历史：登录用户且会话归属本人；`limit` + `beforeMessageIndex` 游标；匿名会话不提供历史。
- 3.1 传入 sessionId 时校验归属；不存在返回 404。

**SSE**

```java
SseEmitter emitter = new SseEmitter(300_000L);
chatService.stream(question, sessionKey, userId, emitter);
return emitter;
```

- 所有事件使用默认 `message`，JSON 内 `type=status/token/followUp/done/error`。
- 每 15 秒发送注释行保活。
- 客户端断开时取消 LLM 订阅。
- `done` 必须返回 `sessionId`、`logId`、`confidence`、`source`、`matchCount`、可选 `recommendations`。
- 错误在流建立前用 HTTP 4xx/429，流建立后用 `error` 事件。

**RAG 流程**

```text
1. QueryRewriteAgent：改写 + 意图分类
2. 长问题 → QueryDecompositionAgent 拆子问题
3. FAQ：
   - VectorRetriever：Chroma topK，过滤 status=1
   - KeywordRetriever：MySQL title/question/answer/keywords LIKE，候选默认 200 条
   - KeywordScorer：字段权重（title 5 / question 4 / keywords 3 / answer 1）+ 词覆盖率 + 短语命中 + 热度，输出 0~1 相关性分数
   - HybridRetriever：按 knowledgeId 合并，使用归一化分数加权融合
   - 用 MySQL 读取最新知识正文，生成 citations
4. ContextCompressor：按查询相关性分配条目预算，按句抽取关键事实，超预算才压缩
5. AnswerAgent：Prompt + LLM 流式生成
6. 写 ask_log：问题、改写 query、回答、confidence、source、matchCount、citations
```

- 未同步向量的知识仍可由 MySQL 关键词分支命中。
- `matchCount` 是合并去重后的知识数。
- 关键词候选默认 200 条，最终按相关性分数取 topK；ACCOUNT/COURSE 只匹配 title/question/keywords，并保留覆盖率门槛。
- 压缩预算默认 2400 字：未超预算原样传入；超出时按条目相关性分配预算，优先保留含查询词、数字、日期、地点、条件句的句子，并保留 `[资料N]` 引用编号。
- 开发期先用 Mock LLM，验证 SSE 和 ask_log，再接真实模型。

**意图与兜底策略**

- 除 CHITCHAT 外，所有意图先做混合检索；ACCOUNT / COURSE 命中知识库时按 FAQ 回答，避免“校园卡补办”“考试安排”等流程问题被意图分支直接跳过。
- 未命中时：ACCOUNT / COURSE 落到统一认证、教务、一卡通等系统引导；FAQ 在 `app.chat.allow-general-answer=true` 时用通用知识回答，并在正文声明“AI 生成、未经校园知识库核实”，关闭时返回“知识库暂未收录”。
- 未命中知识库的通用回答与系统引导，`done.source` 均为 `ai_generated`、`matchCount=0`。
- 多轮上下文：读取当前会话最近 `history-turns` 轮（默认 3 轮，最多 1200 字），用于 `QueryRewriteAgent` 指代消解与 `AnswerAgent` 生成；`ask_log` 仍只记录当前轮问题与回答。

**审核事务**

```java
@Transactional
public void review(Long id, ContributionReviewDTO dto) {
    Contribution c = contributionMapper.selectById(id);
    if (c == null) throw new BizException(CONTRIBUTION_NOT_FOUND);
    if (c.getStatus() != 0) throw new BizException(CONTRIBUTION_REVIEWED);

    // 条件更新防并发重复审核
    int updated = contributionMapper.update(null, Wrappers.<Contribution>lambdaUpdate()
            .eq(Contribution::getId, id)
            .eq(Contribution::getStatus, 0)
            .set(Contribution::getStatus, dto.getStatus())
            .set(Contribution::getReviewRemark, dto.getRemark())
            .set(Contribution::getReviewedBy, SecurityUtils.userId())
            .set(Contribution::getReviewedTime, LocalDateTime.now()));
    if (updated == 0) throw new BizException(CONTRIBUTION_REVIEWED);

    if (dto.getStatus() == 1) {
        Long knowledgeId = knowledgeService.createFromContribution(c, dto.getCategoryId());
        Contribution update = new Contribution();
        update.setId(id);
        update.setKnowledgeId(knowledgeId);
        contributionMapper.updateById(update);
    }
}
```

- `qa` 类型解析 `问：...答：...`；解析失败按普通 article 入库或返回 422。
- 新知识 `vectorStatus=0`。
- 列表需要 username 时，用用户表批量查询或自定义 SQL，避免 N+1。

**提问日志**

- 列表筛选：userId、sessionId、keyword、source、confidence、时间范围。
- 详情附加 `feedbacks`（FeedbackVO 列表），并 join username。
- 返回 `rewrittenQuery`（改写后的检索 query），便于区分“改写质量差”与“知识库缺内容”；旧数据为 null。
- 仅管理员访问；设置日志保留周期。

**批次回滚**

- 可选能力，复用 `AsyncTaskService`，`taskType=BATCH_ROLLBACK`。
- `force=false` 时检查 `knowledge.updateTime > import_batch.createTime`，有修改返回 `20015`。
- 回滚：逻辑删除知识 → 删除 Chroma 向量 → `deleteFile=true` 删 OSS → 批次 `ROLLED_BACK`。
- 与向量化共用单线程队列，避免并发写 Chroma。

**仪表盘**

- 统计知识数、今日提问、回答率、用户数、待审核贡献、热门分类。
- 结果缓存 Redis 5 分钟；统计口径在接口文档 7.1/4.6 中固定。

**落地补充（P8 已于 2026-10-29 完成，口径决定如下）**

- `answerRate` 原文档无公式，定为**知识库命中率**：全部 `ask_log` 中 `source='rag_knowledge_base'`
  且 `confidence <> 'low'`（含 NULL）占比 × 100，保留 1 位小数；走通用回答与兜底空回答都不计入。
- `hotCategories` 定为「启用分类按其下 `status=1` 知识数倒序 TOP3」，与 4.7 的 `knowledgeCount` 同口径。
- 7.16 批次回滚**本期实现**（原为可选）：`BatchRollbackTaskHandler` 复用 `AsyncTaskService` +
  `vectorTaskExecutor` 单线程队列 + `lock:vector`，因此 7.10 的 `20013` 现在覆盖
  `VECTORIZE` 与 `BATCH_ROLLBACK` 两类任务，二者互相排斥。
- 回滚新增一条 `400`：批次仍为 `PROCESSING` 时禁止回滚，避免与导入线程并发改写。
- 部分失败时任务置 `PARTIAL` 且**不**把批次标记 `ROLLED_BACK`，可幂等重试。
- `FileStorageService` 补 `delete(fileUrl)`（本地 + OSS 两个实现），供 `deleteFile=true` 使用。
- 7.12 的同值提交视为无变更：不自增 `token_version`，避免无谓把用户踢下线。
- `20017` 在 HTTP 层不可达（操作者本人必占一个管理员名额），只作为异常数据下的兜底保护，
  已在服务层用单测覆盖。
- **未实现**：提问日志保留周期。自动物理删除 `ask_log` 风险高（隐私数据不可逆、且 6.x 反馈按
  `log_id` 关联），需要产品侧先定保留策略（建议 180 天 + 管理员显式触发的清理任务），本期不动数据。
- 集成测试 `AdminApiIntegrationTest` 5 个用例覆盖用户管理守卫、日志筛选/详情/403/404、仪表盘聚合、
  回滚四类错误码与真实删除链路（`RedisCacheHelper` 用 mock 隔离，本机无 Redis 也能跑）。

### P9 热点/统计/头像/收尾

- 热点：
  - `POST /api/common/hot-topics/{id}/click` 写 Redis ZSET `hot:topic:7d`；

- 统计：

- 头像：
  - 复用 `FileStorageService`，保存到 `avatar/{userId}/{uuid}.{ext}`；
  - 更新 `sys_user.avatar`，旧文件异步清理。
- 收尾：
  - 聊天限流（Redis 计数器，429）；
  - CORS 白名单；
  - Nginx SSE 关闭缓冲；
  - 文件类型/大小校验；
  - Actuator、日志、错误追踪；
  - Docker Compose 与一键启动；
  - 端到端测试与 RAG 评测。

**落地补充（P9 已于 2026-10-29 完成，口径决定如下）**

- **热点排行的两个数据源分工**：Redis ZSET `hot:topic:7d` 只决定**顺序**（score = 去重后的点击数，
  每次点击续期 7 天，形成滚动窗口）；`HotTopicVO.viewCount` 展示的是 MySQL `view_count`。
  原因是 4.5 详情接口本身已在自增 `view_count`，4.2 若再写一次 MySQL 会把一次点击计成两遍。
- **降级与回补**：`ranking()` 返回 `null`（Redis 挂了）走 MySQL `status=1 ORDER BY view_count DESC, id DESC`；
  返回空列表或条目已下架时，剩余名额同样用 MySQL 浏览量补齐。新部署 ZSET 为空也能返回内容，
  不至于让前端热点栏空白。
- **点击去重**：key `view:knowledge:{id}:{ip}`，`setIfAbsent` + 10 分钟窗口（数据库文档 §8 原写 30 分钟，
  以本计划为准，已同步修改 §8）。IP 取 `X-Forwarded-For` 首段，与聊天限流同一套取法。
- 4.2 对**不存在或已下架**的知识静默返回 `code=200, data=null`，不抛 `20001`；
  `limit` 夹取在 1..50，缺省 10。
- **4.6 统计口径**：`totalKnowledge` = `status=1` 且未删除；`todayQuestions` = `ask_log.create_time`
  落在当天 00:00 之后；`totalContributions` = 全部贡献（不区分审核状态，与 7.1 的
  `pendingContributions` 互补）；`totalUsers` = 全部用户。缓存 key `stats:home`，5 分钟。
  首页展示数据不能因为 Redis 不可用而 500，因此读写缓存都包了降级，直查 MySQL。
- **2.6 头像**：原实现直接注入 `AliyunOSSOperator`，本地存储模式下不可用，改为走 `FileStorageService`；
  objectKey 为 `avatar/{userId}/{uuid}.{ext}`；校验 jpg/jpeg/png/gif/webp 与 5MB（`20006`/`20005`，
  空文件 422）；旧头像交给新增的 `FileCleanupService`（`fileCleanupExecutor`）异步删除，
  清理失败只记日志、不影响上传结果。Controller 不再 `throws IOException`。
- **收尾项复用**：聊天限流（`ChatRateLimiter` → 429）、CORS 白名单（`app.cors.allowed-origins`）、
  Actuator（`health,info`）在 P5/P8 已就位，本期只补 Nginx 与 Docker。
- **部署文件**：`behind/Dockerfile`、`frontend/Dockerfile` + `frontend/nginx.conf`
  （`/api/chat/stream` 单独一条 location，`proxy_buffering off` + 长 `proxy_read_timeout`）、
  `deploy/docker-compose.yml`、`deploy/.env.example`。
  Compose 默认 `AI_ENABLED=false`、`AI_EMBEDDING_ENABLED=false`（走 Mock 实现）、`STORAGE_TYPE=local`，
  不填任何密钥也能一键启动；填好 `API_KEY` 后再打开真实模型。
- **测试**：`CommonApiIntegrationTest` 10 个用例，覆盖统计聚合/缓存命中、Redis 排行优先、下架过滤 +
  MySQL 回补、Redis 宕机降级、`limit` 夹取、点击去重与静默忽略、头像 objectKey 与旧文件清理、
  头像三类拒绝、匿名访问边界。Redis 与文件存储用 mock 隔离，本机不启动 Redis 也能跑。
  过程中发现并修掉一个真实缺陷：排行 ID 列表为空时 MyBatis-Plus 会拼出非法的 `IN ()`。
- **未做**：RAG 评测集（需要真实模型 Key 与语料）；Docker 镜像与 Nginx SSE 只做了配置，
  未在本机实际 `docker compose up` 验证。

## 5. 横切代码规范

### 5.1 Controller

```java
@RestController
@RequestMapping("/api/admin/categories")
@RequiredArgsConstructor
public class AdminCategoryController {

    private final CategoryService categoryService;

    @PostMapping
    public Result<Long> create(@Valid @RequestBody CategoryCreateDTO dto) {
        return Result.success(categoryService.create(dto));
    }
}
```

- 只做参数接收、`@Valid`、调用 Service、包装 `Result`。
- 不直接注入 Mapper。
- 不在 Controller 写业务判断。

### 5.2 Service

- 接口放 `service`，实现放 `service/impl`。
- 事务注解加在实现类的写方法上。
- 外部调用（OSS、LLM、Chroma）尽量放在事务外；必须放在事务内时，明确失败补偿。
- 状态流转使用条件更新（`WHERE status = 0`），避免并发重复操作。

### 5.3 Mapper

- 单表 CRUD 用 MyBatis-Plus `BaseMapper` + `LambdaQueryWrapper`。
- 多表列表/统计用自定义 SQL（XML 或 `@Select`），放 `resources/mapper/`。
- 不把业务判断写进 Mapper。

### 5.4 DTO / VO / Entity

- DTO 只放请求字段，加 Bean Validation。
- VO 只放响应字段，不暴露 `password_hash/token_version/deleted`。
- Entity 只映射数据库，不直接返回给前端。
- 分页统一 `PageResultVO`。

### 5.5 异常与错误码

- 业务错误统一 `throw new BizException(ErrorCode.XXX)`。
- 新增错误码必须同步接口文档 1.2 和 `ErrorCode` 枚举。
- 401/403 由 Security 处理，业务 Service 不手写 HTTP 状态。

### 5.6 权限

- 路径级权限在 `SecurityConfig`。
- 数据归属在 Service 校验：
  - 会话只能本人访问；
  - 反馈只能操作自己的日志；
  - 管理员接口统一 `ROLE_ADMIN`；
  - 用户禁用/角色修改禁止操作自己或最后一个管理员。

### 5.7 缓存与异步

- Redis key 与数据库文档第 8 节保持一致。
- 缓存只缓存可重建数据（分类、统计、热点），业务事实以 MySQL 为准。
- 异步任务必须落 `async_task`，不能只靠内存状态。
- 任务执行器单线程，避免 Chroma 并发写。
